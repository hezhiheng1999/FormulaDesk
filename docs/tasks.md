# FormulaDesk 任务管理

本项目采用串行工作方式：一个项目管理对话负责需求与优先级，每项独立改进或升级在 FormulaDesk 项目中新开一个执行对话。本文是任务范围、状态和交接结果的唯一清单；[项目背景](project-context.md)保留版本、架构和验证边界。

## 对话与文件分工

- 管理对话负责讨论候选需求、选定下一目标和验收标准、查看完成结果，以及维护本管理规则。
- 执行对话负责一个目标的实现、适用验证、相关反馈修复和结果记录。同一目标的修复留在原对话；独立的新需求返回候选清单，另开对话。
- 同一时间只有一个执行对话修改本项目。执行期间由它维护对应任务记录；管理对话可讨论需求，但不同时改写共享文件。下一项实施须等前一项实现、验证和文件状态交接完成。
- 已确认目标并要求开始时，直接在本项目中新建执行对话，标题为 `FD-001 · 具体目标`，不重复询问是否新开对话。只有候选想法时不创建执行对话。
- 所有执行对话复用本项目目录。新对话不隔离文件，也不默认创建分支或 worktree；以后需要并行开发时再单独约定隔离与集成方式。

任务编号按 `FD-001`、`FD-002` 顺序分配，不复用，也不与版本号绑定。一个发布版本可以包含多项已完成任务。

## 启动、实施与交接

1. 在管理对话确定一个目标，写清范围、可检查的验收条件，以及本次 Git 操作授权。按任务大小编写必要说明，不为小改动重复创建计划、进度和总结文件。
2. 分配编号、建立任务记录，在 FormulaDesk 项目中新建执行对话，将目标、验收条件和授权写入启动消息。对话编号及本机材料存入忽略的 `.local-history/tasks/FD-001/`，公开文档不记录私人对话内容或本机绝对路径。
3. 执行对话先读 AGENTS.md、项目背景和对应任务记录，按需读取开发与测试说明；核对实际目录、分支、HEAD 和未提交改动，记录基线与已有改动归属。保留已有文件，不把新对话视为干净工作树。
4. 持续实现并完成适用验证。需要用户决定且确实影响后续工作时，记录具体问题和已完成部分；发现独立需求先记候选，不扩大当前任务。
5. 更新任务记录，给出实际变化、验证结果、未验证范围和代码状态。只执行本任务已授权的提交、推送或发布。管理对话依据该记录确定下一项工作，无需重新梳理整个聊天历史。

状态使用“待启动、进行中、待决策、已完成、已取消”。只有验收条件及必要验证均已满足，才记为“已完成”；依赖用户操作的必要验证尚未完成时保留待办，不能用静态检查替代。记录一个当前检查点即可，不追加逐轮聊天日志。

实现状态与 Git/发布状态分开：任务可完成实现和验证但尚未提交，必须明确写出改动文件归属；下一项任务不能把这些改动误当作自己的基线。原任务的提交、推送和发布授权不自动延续给下一项。

## 任务记录模板

在本文追加一份记录，并就地更新其当前状态；不要在项目背景或本机交接文件中再维护一份任务进度。

```text
FD-<编号> · <具体目标>
状态：待启动 / 进行中 / 待决策 / 已完成 / 已取消
目标与范围：
验收条件：
基线：分支、HEAD、已有未提交改动及其归属
本次 Git 授权：本地提交 / 推送 / 标签与 Release，逐项明确
当前检查点：已完成内容；剩余工作；需要的决定
验证：实际命令或交互、环境、结果、对应成品；未验证范围
代码与发布状态：未提交文件归属 / 提交 SHA；是否推送、是否发布
```

未明确授权的 Git 操作不执行。无需永久草稿、联网或新依赖的任务按既有项目规则实施；任务确实需要新增这些能力时，先说明具体影响，确认当前任务授权涵盖它们。

若原对话因故无法继续，接续同一任务时沿用编号和当前检查点，核对文件状态，并在本机记录中关联原对话；不把同一项未完成工作登记为新的改进。
